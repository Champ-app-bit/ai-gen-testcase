คุณคือ **ประตูหน้า** ของระบบสร้างเทสอัตโนมัติ
เป้าหมายเดียว: **ผู้ใช้ต้องจำแค่คำสั่งนี้คำสั่งเดียว** ที่เหลือคุณดูสถานะแล้วพาไปขั้นถัดไปเอง

**Input:** $ARGUMENTS

## หลักการ
- **ห้ามให้ผู้ใช้ต้องรู้ว่าระบบมีกี่คำสั่ง** — ถ้าขั้นถัดไปคือ `/module-scout` ก็ทำให้เลย ไม่ใช่บอกให้ไปพิมพ์เอง
- **ห้ามถามสิ่งที่หาเองได้** — path, stack, ext, ignore ทั้งหมดตรวจเองได้ ถามเฉพาะที่เดาไม่ได้จริงๆ
- ทุกครั้งที่จบ ให้บอก 2 อย่างเสมอ: **ตอนนี้อยู่ตรงไหน** และ **พิมพ์อะไรเพื่อไปต่อ**
- ห้าม `git commit` / `push` · ห้ามแตะโค้ด product

## 0. หา repo เครื่องมือก่อน
ต้องรันจากโฟลเดอร์ที่มี `scripts/` + `projects/` — ถ้า cwd ไม่ใช่:
```bash
find ~ -maxdepth 5 -name bootstrap_project.py -path '*/scripts/*' 2>/dev/null | head -1
```
หาไม่เจอ → บอกผู้ใช้ว่าต้องระบุ path ของ repo เครื่องมือ แล้วหยุด **ห้ามเดา**

## 1. ไม่มี argument → แสดงแผงสถานะ
สแกน `projects/*.yaml` (ไม่รวม `*.local.yaml`, `_local.example.yaml`) แล้วแสดงตารางเดียว:

| project | ระดับ | ทำไปแล้ว | ขั้นถัดไป |
|---|---|---|---|

- **ระดับ** ตรวจแบบเดียวกับ `/gen-batch` ขั้นที่ 0: L0 ยังไม่ setup · L1 ยังไม่มี suite · L2 พร้อมปล่อยรัน
- **ทำไปแล้ว** อ่านจาก `<batch.dir>/modules.yaml` ถ้ามี (`python3 scripts/batch_state.py report <p>`)
- ปิดท้ายด้วยวิธีเพิ่ม project ใหม่: `/testgen <path ของ repo>` หรือ `/testgen <ชื่อใหม่>`

## 2. มี argument → ตัดสินว่าเป็นอะไร

- **มี `--answer`** → โหมด **เคลียร์คำถามค้างทีเดียว** (ข้อ 5) — ทำก่อนอย่างอื่นเสมอ
  เพราะคำตอบอาจเปลี่ยนของที่ทำไปแล้ว
- **มี `--report`** → รัน `python3 scripts/make_report.py <project>` แล้วสรุปหัวข้อสำคัญให้ผู้ใช้อ่านในแชท
  (รายงานเต็มอยู่ที่ `<batch.dir>/report.md`) แล้วจบ

- **เป็น path ที่มีอยู่จริง** (`test -d`) → โหมด **เพิ่ม project ใหม่** (ข้อ 3) โดยตั้งชื่อจาก basename ของโฟลเดอร์ (ให้ผู้ใช้ยืนยัน/แก้ได้)
- **ตรงกับ `projects/<ชื่อ>.yaml` ที่มีอยู่** → โหมด **ไปต่อ** (ข้อ 4)
- **ไม่ตรงอะไรเลย** → ถามว่าจะสร้าง project ใหม่ชื่อนี้ไหม ถ้าใช่ → ข้อ 3 (ต้องขอ path repo)

## 3. โหมดเพิ่ม project ใหม่ (จากศูนย์ → พร้อมใช้)

**เป้าหมาย: ผู้ใช้ไม่ต้องเขียน YAML เองแม้แต่บรรทัดเดียว**

1. **หา repo ที่เกี่ยว** — จาก path ที่ผู้ใช้ให้ ถ้าเป็นโฟลเดอร์แม่ที่มี repo ย่อย (`frontend/`, `backend/`, `api/`)
   ให้เสนอรายการที่เจอแล้วให้ยืนยัน · ถ้ามีแค่ path เดียวก็ใช้ตัวนั้น
2. **ถามเฉพาะ 2 อย่างที่ตรวจเองไม่ได้** (ใช้ AskUserQuestion รวบครั้งเดียว ห้ามถามทีละข้อ):
   - **repo automation** จะเก็บเทสไว้ที่ไหน (เสนอ candidate ที่หาเจอในเครื่อง + ตัวเลือก "สร้างใหม่ที่ `<path>_automation_script`")
   - **โดเมนของระบบ 1 บรรทัด** (เช่น "ระบบบริหารคลังวัสดุ") — ช่วยให้ทุก stage เดาบริบทถูก
   - เอกสาร spec ถ้าเจอโฟลเดอร์ที่เข้าเค้า (`docs/`, `.cursor/prp/`) ให้เสนอเป็นตัวเลือกในคำถามเดียวกัน
3. **รัน bootstrap** — สร้าง config ทั้งสองไฟล์ให้อัตโนมัติ:
   ```bash
   python3 scripts/bootstrap_project.py <ชื่อ> --code <path> [--code <path>...] \
       [--specs <path>] --automation <path> --domain "<โดเมน>"
   ```
   มันตรวจ stack เอง (NestJS/Next/Vue/Laravel/Express/Django/Spring + monorepo) แล้วเขียน
   `include_ext` / `ignore_dirs` / `signal_dirs` / `discovery` ที่**ทดสอบ glob กับดิสก์จริงแล้ว**
4. **ตรวจผลด้วยตา แล้วแก้ถ้าผิด** — เปิด `projects/<ชื่อ>.yaml` ดู:
   - `discovery` ชี้ถูกที่ไหม (ดูจำนวนที่ match + ชื่อตัวอย่างใน comment ท้ายบรรทัด)
   - stack ไหนตรวจไม่ออก (`unknown`) → หา marker เองแล้วเติม glob ให้ + **เสนอเพิ่ม stack นั้นเข้า `scripts/bootstrap_project.py`** เพื่อให้ project หน้าไม่ต้องมาแก้อีก
5. **ต่อด้วย `/module-scout <ชื่อ>` ทันที** (ทำให้เลย ไม่ต้องให้ผู้ใช้พิมพ์) → ได้ทะเบียน module + อันดับความเสี่ยง
6. รายงาน: เจอกี่ module · เสี่ยงสูงกี่ตัว · **ขั้นถัดไปคือ `/testgen <ชื่อ>` เพื่อเริ่มทำเทส**

## 4. โหมดไปต่อ (project ที่ setup แล้ว)

ตรวจสถานะแล้วทำขั้นที่ค้างอยู่ **โดยไม่ต้องถามซ้ำในสิ่งที่รู้อยู่แล้ว**:

| สถานะที่ตรวจได้ | ทำอะไร |
|---|---|
| ไม่มี `<p>.local.yaml` | เรียก `/setup <p>` (path บนเครื่องนี้ยังไม่รู้) |
| ไม่มี `modules.yaml` | เรียก `/module-scout <p>` |
| มีทะเบียนแล้ว | เรียก `/gen-batch <p>` (มันจะตัดสินเอง ว่าเข้า PILOT หรือ BATCH) |
| มีงานค้าง `in_progress` | บอกว่าค้างที่ module ไหน stage ไหน แล้วไปต่อจากตรงนั้น |
| มีคำถามค้างในคิว | บอกจำนวน + path **ก่อน**เริ่มงานใหม่ (คำตอบอาจเปลี่ยนของที่ทำไปแล้ว) |

ส่ง argument เพิ่มที่ผู้ใช้พิมพ์มา (เช่น `--limit 3`) ต่อไปให้คำสั่งปลายทางด้วย

## 5. โหมด `--answer` — เคลียร์คำถามค้างทีเดียวจบ

เป้าหมาย: ผู้ใช้เสียเวลาครั้งเดียว ตอบรวบทุกข้อ แล้วระบบไปจัดการผลกระทบเองทั้งหมด

1. **รวบคำถาม** จาก `<batch.dir>/questions/*.md` (รูปแบบ 1 ข้อ = 1 แถวตาราง:
   `| คำถาม | ตัวเลือก | สมมติฐานที่ใช้ไปก่อน | ผลถ้าสมมติฐานผิด | Evidence file:line |`)
   ข้ามแถวที่มีคำตอบแล้ว (ขึ้นต้นด้วย `✔`)
2. **เรียงลำดับความสำคัญ** — ข้อที่ "ผลถ้าสมมติฐานผิด" กระทบเทสหลายเคส หรืออยู่ใน module `risk: high` ขึ้นก่อน
   **บอกจำนวนทั้งหมดก่อนเริ่มถาม** เพื่อให้ผู้ใช้รู้ว่าต้องใช้เวลาแค่ไหน
3. **ถามด้วย AskUserQuestion ทีละไม่เกิน 4 ข้อต่อครั้ง** — ทุกข้อต้องแนบในคำอธิบายตัวเลือก:
   สมมติฐานที่ระบบใช้ไปก่อนแล้ว · ผลถ้าผิด · `file:line` ที่เป็นที่มา
   ตัวเลือกต้องมี **"ยังไม่ตอบ ข้ามไปก่อน"** ทุกครั้ง — บังคับให้เดาไม่ได้
4. **เขียนคำตอบกลับไฟล์ทันทีทุกชุด** (ไม่ใช่ตอนจบ — ถูกตัดกลางคันแล้วคำตอบต้องไม่หาย):
   แก้แถวนั้นให้ขึ้นต้นด้วย `✔` แล้วต่อท้ายคอลัมน์ `คำตอบ` + วันที่ + ชื่อผู้ตอบ
5. **จัดการผลกระทบต่อ (นี่คือส่วนที่ทำให้ `--answer` มีค่ามากกว่าการตอบในไฟล์เอง)** — ต่อ module:
   | เจออะไร | ทำอะไร |
   |---|---|
   | คำถามของ module นั้นถูกตอบครบ | เรียก `/gen-behavior-spec promote <module> --project <p>` |
   | คำตอบ **ขัดกับสมมติฐานเดิม** | `batch_state.py set <p> <module> --stage testcases --status pending --note "คำตอบเปลี่ยนสมมติฐาน ต้องทำเทสเคสใหม่"` — ของที่ generate จากสมมติฐานผิด ต้องถือว่าใช้ไม่ได้ |
   | คำตอบบอกว่า **เป็นบั๊ก** | ต่อท้าย `<batch.dir>/findings.md` แล้วเขียน spec ตามพฤติกรรมที่ *ควรเป็น* พร้อม mark `⚠️ โค้ดปัจจุบันยังไม่ตรง spec ข้อนี้` |
   | ยังตอบไม่ครบ | คง `status: draft` ไว้ **ห้าม promote** และบอกว่าเหลือข้อไหน |
6. **สรุป**: ตอบไปกี่ข้อ · promote ได้กี่ module · ต้องทำเทสเคสใหม่กี่ module (เพราะสมมติฐานผิด) ·
   บั๊กที่ยืนยันใหม่กี่ข้อ · เหลือค้างกี่ข้อ · แล้วบอกให้สั่ง `./testgen <p>` ต่อเพื่อเดินสายพานใหม่

## 6. ปล่อยรันยาวข้ามคืน → ให้ใช้ตัวรันนอก Claude Code

ถ้าผู้ใช้ขอ "รันทั้ง project" / "ปล่อยไว้ข้ามคืน" / "ไม่อยากนั่งเฝ้า" — **อย่ารับทำเองในบทสนทนานี้**
เพราะโควตาหมดกลางทาง = session ตาย แล้วไม่มีใครสั่งใหม่ ให้บอกให้ออกไปรันคำสั่งเดียวนี้แทน:

```bash
cd <repo เครื่องมือ> && ./testgen <project>          # เดินจนหมด นอนรอโควตาเอง จบแล้วออกรายงาน
./testgen <project> --max 5                          # ลองแค่ 5 module ก่อน
./testgen <project> --dry-run                        # ดูลำดับงานก่อน ไม่เรียก claude ไม่แก้ทะเบียน
```

ในบทสนทนานี้เหมาะกับ: PILOT ตัวแรก (ต้องมีคนตัดสิน convention), `--answer`, `--report`, และการดูของทีละชิ้น

## ข้อกำหนด
- **ตอบเป็นภาษาไทย** · สั้น ตรง บอกสถานะกับขั้นถัดไปเสมอ
- ถามผู้ใช้ **ไม่เกิน 1 ครั้งต่อการรัน 1 รอบ** (รวบทุกคำถามไว้ใน AskUserQuestion เดียว)
  — **ยกเว้นโหมด `--answer`** ที่หน้าที่คือถามให้จบ: ถามเป็นชุดละไม่เกิน 4 ข้อได้จนหมดคิว
- ห้ามรายงานว่าเสร็จถ้าขั้นที่เรียกไปยังไม่จบ · ห้ามเดา path
